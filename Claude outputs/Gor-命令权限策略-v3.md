# Gor 命令权限策略 v3（按落笔模式区分）

> 日期：2026-10-16
> 替代：Gor-命令权限策略-v2.md
> 依据：项目中的落笔模式。`editMode` 取值 `auto`（界面名"即刻落笔"）与 `review`（界面名"审阅落笔"），在 `Server/routes/chat.py` 发送时读取并冻结，`Server/db/project_changes.py` 的 `get_edit_mode` 提供偏好。

## 一、核心规则

1. **权限随落笔模式变化**：同一条命令，在"即刻落笔"和"审阅落笔"下可能得到不同结论。
2. **模式在发送瞬间冻结**：与现有 `edit_mode` 一致，运行中切换模式不影响本轮。
3. **"本地项目"定义**：当前连接的工作区根目录（Web 为该项目的虚拟文件系统，插件为 VS Code 已打开的 workspace folder）。路径先做真实路径解析（去掉 `..`、解析符号链接），再判断是否落在根目录之内。
4. **未匹配的命令默认确认**：不在白名单中的命令，两种模式都需要确认（见第三节待定项）。

## 二、判定表

| 类别 | 即刻落笔 (`auto`) | 审阅落笔 (`review`) |
|---|---|---|
| git 只读（status、log、diff、show、branch 列出） | 直接执行 | 直接执行 |
| git 写入（commit、add、checkout、switch、merge、rebase、reset、stash、tag） | 直接执行 | 直接执行 |
| **git 删除分支**（`branch -d/-D`、`branch --delete`） | **确认** | **确认** |
| node / npm / npx / pnpm / yarn 运行与安装（`node`、`npm run`、`npm test`、`npm install`、`npx` 等） | 直接执行 | 直接执行 |
| 项目内文件的增、删、改、查 | 直接执行 | 直接执行（写入结果仍进入候选，需在"落笔"中确认才真正生效） |
| **删除文件或目录**（`rm`、`rmdir`、`unlink`、`git clean`、`git rm`） | **确认** | **确认** |
| **删除项目** | **确认** | **确认** |
| **本地项目外**的文件增、删、改、查 | **确认** | **确认** |
| 白名单之外的命令 | **确认**（建议，见待定项） | **确认** |
| 始终禁止（强制推送、发布、读取密钥、`env` 输出） | 禁止 | 禁止 |

说明：
- "项目内文件增删改查"在审阅落笔下仍会生成候选，不会直接写入项目；这是现有的 ChangeSet 落笔流程，不需要再弹一次命令确认。
- "删除文件"在两种模式下都需要确认，因为即使在审阅落笔下，删除在候选里也要等待用户确认才生效。
- 与 v2 的差异：v2 中"写入项目之外的路径"是**禁止**；v3 改为**确认**，因为你希望允许在确认后处理本地其他文件。

## 三、待你确认的两点

1. **即刻落笔下，白名单之外的命令怎么办？**
   - 建议 A（我的推荐）：确认。理由：白名单之外的命令无法预先判断风险，默认确认最稳。
   - 建议 B：直接执行并记录审计。与"即刻"的定义更贴近，但风险更高。
2. **"白名单"具体包含哪些命令？** 目前按第二节的"直接执行"类别理解。如果你希望白名单更窄（例如 node 只允许 `run`、`test`，不允许 `install`），请告诉我。

## 四、执行环境前提

- **沙箱执行（Runner）**：容器无网络（依赖安装只通过白名单代理）、根文件系统只读、只有 `/work` 可写、没有宿主机挂载。因此在沙箱里，"项目外的本地文件"实际上不可访问，这类请求会直接失败，不需要确认。确认规则主要用于**插件端本地执行**。
- **插件端本地执行**：`npm install` 会运行项目里的安装脚本，风险等同于任意代码。若采用本地执行，需要额外开启 VS Code 工作区信任（Workspace Trust）检查；未信任的工作区，node 与 python 命令一律确认。这一条超出本策略的放开范围，需要单独确认。

## 五、实现要点

1. 策略以数据形式存放，例如 `shared/command-policy.json`，结构为"类别 × 模式 → 决定"（`allow` / `confirm` / `deny`）。服务端和插件端读取同一份。
2. 判定顺序：先匹配 `deny`，再匹配 `confirm`，再匹配 `allow`；都不匹配则为 `confirm`。
3. 路径判断：先解析真实路径，再与工作区根目录比较；无法解析或解析失败，按"本地项目外"处理（即确认）。
4. 确认请求通过服务端聊天流程发起，复用现有落笔确认界面的样式与组件，插件只执行带一次性批准 ID 的请求。
5. 审计：每条命令记录模式、类别、判定结果（allow/confirm/deny）、用户是否确认、工作目录、退出码、耗时。
6. 测试：为两种模式各写一组判定用例，覆盖：分支删除、项目外路径（包括 `..` 与符号链接）、白名单外命令、审阅模式下的候选流程。

## 六、判定伪代码

```
def decide(command, mode, path_scope):
    if is_forbidden(command):
        return "deny"
    if is_branch_delete(command) or is_file_delete(command) or is_project_delete(command):
        return "confirm"
    if path_scope == "outside_project":          # 本地项目外的增删改查
        return "confirm"
    if not is_whitelisted(command):              # 白名单之外
        return "confirm"                         # 两种模式都确认（待定项 1 可改为 auto 直接执行）
    return "allow"
```

注意：`mode` 在这段伪代码里只影响"白名单之外"这一条的最终取值（见待定项 1）。其余规则两种模式一致，这是有意为之，因为删除和项目外操作的风险与模式无关。
